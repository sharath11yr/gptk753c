Now, let’s talk about the most common mistake I see in the comments and in interviews. It is the 'Database First' mentality.

Many applicants start a design by saying, 'I will use a SQL database.' Or 'I will use MongoDB.' They draw the database box immediately. But here is the reality: The database is usually the bottleneck. It is the hardest part to scale. If you start with the database, you are painting yourself into a corner.

Instead, the principal engineer approach is: 'What is the read-to-write ratio? If I have 10,000 reads for every 1 write, do I need a complex relational database, or can I use a cache and a simpler store?'

Most juniors get this wrong because they assume every system needs a heavy database. But think about a social media feed. Do you need complex joins there? No. You need speed. You need a system optimized for that specific problem.

Let’s look at a concrete example. If you are building a URL shortener, the read-to-write ratio is extremely high. In that case, you would not start with a complex relational database schema. You would use a simple key-value store like Redis.

Here is the critical step. To set a key-value pair in Redis, the exact command is:

```bash
SET url_123 "https://example.com"
```

And to get it back, the exact command is:

```bash
GET url_123
```

This is your 'final check' step. Open your terminal. Run the `SET` command. If the output returns `OK`, your architecture choice for that specific constraint of high read volume and simple data structure is validated. If you are using PostgreSQL for a simple URL shortener, you would check the schema migration time and query performance, and likely find it insufficient for the scale due to the overhead of ACID compliance for simple key-value data.

[MYTHS AND PRO TIPS]

Let’s bust a myth right now. The myth is that you need to know every technology under the sun.

You do not. What you need is depth over breadth. It is better to know how one caching layer works—how Redis handles eviction policies, for example—and when to use it, than to list ten technologies you have never touched.

A pro tip for your next interview: When asked about a component, always discuss the 'Trade-offs'.

Say this: 'I would use X for this reason, but if we had constraint Y, I would switch to Z.'

That sentence alone signals to the interviewer that you understand the architecture, not just the buzzwords.

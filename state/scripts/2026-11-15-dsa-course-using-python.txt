[STEP 1: THE FOUNDATION]

Let us start with the elephant in the room. What is Big O notation? In plain English, Big O is not a measure of how long your code takes to run in seconds. It is a measure of how your code’s runtime grows as the input size grows. We use letters like O(n), O(log n), and O(1). But what do they actually mean?

Imagine you have a phone book with 100 names. If the book is sorted alphabetically, you can open to the middle, see if the name is earlier or later, and cut the search space in half. This is binary search. In Big O terms, that is O(log n). Even if the phone book grew to a million names, you would only need about 20 steps to find your person. That is the power of logarithmic growth.

Now, contrast that with a linear search. You start at the first name and look at every single name until you find the one you want. If the phone book has 100 names, you might have to look at all 100. If it has 1,000 names, you look at 1,000. This is O(n). The 'n' stands for the number of inputs. If you double the input size, you double the time it takes.

Here is the everyday analogy I want you to remember. Imagine you are at a party and you want to find someone who is holding a red balloon. If you ask everyone one by one, that is a linear search. The more people at the party, the longer it takes. But if the party organizer tells you, 'The red balloon is always near the punch bowl,' and you walk straight there, that is O(1) constant time. It does not matter if there are 10 people or 1,000 people; you go to the same spot.

In Python, we see this constantly. If you want to get the first item in a list, you type `my_list[0]`. Whether that list has 10 items or 10 million items, Python retrieves that first item instantly. That is O(1). But if you want to check if a number is in an unsorted list, you might have to scan every item. That is O(n).

But here is the part most people get wrong. Beginners often obsess over O(n) being 'bad.' They see O(n^2) and panic. But in an interview, the goal is not to have the most complex code. The goal is to have code that scales. We will get to that mistake in a moment. For now, understand this: O(1) is perfect, O(log n) is excellent, O(n) is acceptable for small data, and O(n^2) is usually a red flag unless the data is tiny. Keep this in the back of your mind as we write our first actual function.

[STEP 2: SOLVING THE PROBLEM]

Enough theory. Let us solve your first interview problem. The problem is this: Given an array of integers, find the two numbers that add up to a specific target sum. This is a classic. In Python, you might be tempted to write a nested loop. You take the first number, and you loop through the rest of the list to see if any other number adds up to the target. That approach works, but its Big O is O(n^2). For every single element, you are looping through the entire remaining list. If the array has 1,000 elements, you are performing nearly a million operations. That is too slow for a interview setting.

The optimized solution uses a Hash Map. In Python, we use a dictionary. The logic is brilliant in its simplicity. We iterate through the list just once. For each number, we calculate the 'complement.' The complement is simply the target sum minus the current number. We check if that complement is already in our dictionary. If it is, we have found our pair. If it is not, we add the current number to the dictionary with its index, and we move to the next number.

Let me write this out for you. We start with an empty dictionary. Let's say our target is 10, and our array is [2, 7, 11, 15].

First iteration: The current number is 2. The complement is 10 minus 2, which is 8. Is 8 in our dictionary? No. So we add 2 to the dictionary. Dictionary now looks like {2: 0}.

Second iteration: The current number is 7. The complement is 10 minus 7, which is 3. Is 3 in our dictionary? No. We add 7. Dictionary is now {2: 0, 7: 1}.

Third iteration: The current number is 11. The complement is 10 minus 11, which is -1. Is -1 in our dictionary? No. We add 11.

Fourth iteration: The current number is 15. The complement is 10 minus 15, which is -5. Is -5 in our dictionary? No. We add 15.

Wait, I just spoiled the example. In a real interview, the input would be crafted so the answer exists. Let's adjust the array to [2, 7, 11, 5] with target 9.

First iteration: Number is 2. Complement is 7. Dictionary is empty. Add 2.

Second iteration: Number is 7. Complement is 2. Is 2 in the dictionary? Yes! It is at index 0. We have found our pair: indices 0 and 1. The numbers are 2 and 7.

This solution runs in O(n) time. We only loop through the list once. And because dictionary lookups in Python are on average O(1), we are not adding any hidden loops. The space complexity is also O(n) because, in the worst case, we might store every single number in the dictionary. But time-wise, we have crushed the O(n^2) brute force approach.

[COMMON MISTAKES AND PRO TIPS]

Now, let us talk about the mistakes I see constantly in the comments and on student code.

Mistake number one: Ignoring edge cases. In the haste to write the solution, students forget that the array might be empty, or that there might be no solution. In an interview, if you do not mention these, the interviewer will probe you. Always ask: 'What if the list is empty?' or 'What if no two numbers add up to the target?' A pro tip is to return an empty list or a specific error message in those cases.

Mistake number two: Using the wrong data structure. I mentioned the dictionary is O(1) for lookups. But some beginners try to use a list to store seen numbers. Checking if an item is in a list is O(n). If you do that inside your main loop, you accidentally revert your solution back to O(n^2). Always use a set or a dictionary for the 'seen' values.

Mistake number three: Overcomplicating the Big O analysis. Students will try to count every single operation. 'If I do this swap, that is one operation, and this comparison is another.' Stop. In Big O, we drop the constants. We care about the growth rate. Whether you do 100 operations or 1,000 operations for n items, the growth is still linear, O(n). Focus on the shape of the curve, not the exact height.

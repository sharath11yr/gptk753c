First up, Project Number One: A Command-Line Todo List Manager. This is the 'Hello World' of employable projects, but we're going to level it up. Every hiring manager knows the basic todo list. To make yours stand out, you need to handle data persistence. That means when you close the program, the tasks must still be there when you reopen it. We are going to use file handling in C. Specifically, we will use text-based file I/O using `fprintf` and `fscanf` to save your list to a plain text file. It sounds intuitive, but think of it like writing a list on a notepad. You write your tasks down, and when you come back, everything is exactly where you left it, readable by any text editor.

Here is the step-by-step code structure. First, we define a struct for our task. It will have an ID, a description, and a status. We will then create a function to save this struct to a file called 'tasks.txt'. We will use `fopen` with the mode 'w' to write text. Then, `fprintf`, passing the formatted fields of the struct to the file pointer. To load it back, we switch to 'r' mode and use `fscanf`. The magic here is that the computer reads human-readable characters. This project teaches you string manipulation and file I/O, which are core C skills.

But here is the part most people get wrong. They try to use binary files with `fwrite` and `fread`. That is a trap. Binary files are architecture-dependent; if the code is compiled on a different compiler or run on a different system, the data will be unreadable. Text files are robust. A user can open 'tasks.txt' in Notepad or VS Code and see their data. That is the pro tip for this project: always use text mode for data structures that need to be portable.

Moving on to Project Number Two: A Basic Calculator with History. This project tests your understanding of functions, loops, and switch statements. But we are going to add a twist: a history log. You know how calculators have a 'last answer' feature? We are going to implement that. The user will perform a calculation, and the result will be appended to a text file called 'history.log'.

The step-by-step process is this. We open the file in append mode, 'a'. This is crucial. If you open it in 'w' mode, you will wipe the history every time you run the program. Using `fprintf`, we write the expression and the result to a new line. To read the history back, we switch to read mode, 'r', and use a while loop with `fscanf` to pull each line out. The analogy here is a receipt tape. Every time you buy something, the machine pulls out a bit of paper. You don't overwrite the previous receipt; you just add a new one.

The common mistake here? Beginners forget to close the file. In C, if you don't close the file, the data might not actually write to the disk until the program exits, or worse, you corrupt the file. Always use `fclose`. It is the simplest line of code, but it prevents hours of debugging.

Project Three: A Temperature Converter with Validation. This is the project that tests your ability to handle user input, which is the number one source of bugs in C. We are going to build a program that asks for a temperature in Celsius and converts it to Fahrenheit, but we are going to validate the input. We don't want the user typing 'abc' and crashing the program.

The step-by-step logic uses a do-while loop. Inside the loop, we use `fgets` to read a line of input into a buffer. We then use `sscanf` to parse the number from that string. This method completely avoids the buffer clearing nightmare. Then, we check if the number is within a reasonable range. If it's not, we print an error and loop again. The analogy is a bouncer at a club. The bouncer checks the ID (the input). If it's valid, they let you in (the calculation). If not, they say 'Sorry, try again.'

The mistake most people make with input validation is using `scanf` directly and trying to clear the buffer with `while(getchar() != '\n')`. As we discussed, this can block or fail. The correct way is to use `fgets` to get the line, and `sscanf` to extract the value. If `sscanf` returns zero, the user did not type a number. You must ask again. That is the difference between a robust program and one that crashes.
